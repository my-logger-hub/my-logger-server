# my-logger-server — gRPC contract

Документ фиксирует контракт между UI и сервером. Любое расхождение в реализации с этим документом — баг.

## Time-range contract

Все методы, принимающие диапазон по времени (`Read`, `ScanAndSearch`), используют единое правило кодирования полей `from_time` (`int64`) и `to_time` (`int64`). UI обязан шифровать одно из трёх состояний; сервер обязан декодировать в той же логике.

### Состояния

| Состояние UI                          | `from_time`                                | `to_time`        | Семантика на сервере                              |
|----------------------------------------|--------------------------------------------|------------------|---------------------------------------------------|
| `HoursAgo(N)`, `N >= 0`                | `-N` (для `N=0` это `0`)                   | `0`              | один шард (один час) = `now + from_time часов`    |
| `ExactHour(date_key)`                  | `date_key` в формате `YYYYMMDDHH` (>= `2024010100`) | `0`     | один шард (один час) по абсолютному ключу         |
| `Range(from_us, to_us)`                | unix-микросекунды (>0)                     | unix-микросекунды (>0) | диапазон шардов `[from_us..to_us]`           |

### Алгоритм декодирования (сервер)

```
if to_time == 0:
    if from_time <= 0:
        # «смещение в часах от текущего времени»
        date_key = DateHourKey(now + from_time hours)
    else:
        # «абсолютный date_key YYYYMMDDHH»
        date_key = DateHourKey(from_time)
    → читать ОДИН шард
else:
    # «диапазон в unix-микросекундах»
    → читать ВСЕ шарды, чьи часы попадают в [from_time .. to_time]
```

### Реализация на стороне UI

[`models/time_range.rs::TimeRange::get_date_from_date_to`](https://github.com/MyJetTools/MyLogger/blob/main/my-logger-ui/src/models/time_range.rs):

```rust
match self {
    HoursAgo(n)         => (-(n as i64), 0),
    Range(from, to)     => (from.unix_us, to.unix_us),
    ExactHour(date_key) => (date_key.value, 0),
}
```

### Реализация на стороне сервера

[`grpc_server/my_logger_grpc_service.rs`](../src/grpc_server/my_logger_grpc_service.rs) — оба метода `read` и `scan_and_search` зовут единую функцию `RequestType::from_request(from_time, to_time)`. Логика парсинга существует ровно в одном месте:

```rust
if to_time == 0 {
    if from_time <= 0 {
        DateHourKey::from(now.add_hours(from_time))
    } else {
        DateHourKey::from(from_time)
    }
} else {
    DateRange(from_time.into(), to_time.into())
}
```

### Запрещено

- Положительные `from_time < 2024010100` при `to_time == 0` — UI такие не присылает; если придёт, сервер интерпретирует как невалидный date_key и вернёт пустой результат.
- `to_time < 0` — не поддерживается.
- `from_time > to_time` при range-режиме — поведение не определено (вернётся пустой результат).

## Search modes

Любой поиск ограничен интервалом и `take` и идёт в одну из двух сторон — до другого конца интервала или до `take` подходящих записей, что наступит раньше:

- **вверх** — от начала интервала, старые первыми: часы по порядку, каждый читается вперёд от ячейки индекса первой секунды интервала;
- **вниз** — от конца интервала, новые первыми: нижняя секунда находится по индексу (он в памяти) — от конца интервала вниз, пока `count` секунд не сложатся в `take` и не меньше чем в одно чтение (64 KiB локально, 1 MiB из S3); дальше данные читаются от неё вверх одним проходом. С фильтром по уровню или индексированным ключам вместо `count` берутся счётчики `index-by-key` для их значений — точные для одного ключа, верхняя граница для нескольких или с фразой: если подходящих не хватило, следующая нижняя секунда находится так же — на недостающее, с поправкой на долю подходящих. Секунды без совпадений не читаются; промежуток между подходящими секундами читается насквозь, только если в нём меньше записей, чем помещается в одно чтение.

Записи, которые ещё ждут записи на диск, тоже участвуют.

### `SearchUp` / `SearchDown` gRPC

Один запрос `SearchLogsRequest` на оба направления: `from_time`, `to_time` (кодируются как в `Read`), `take`, `levels`, `context_keys`, `phrase`. Фильтры действуют вместе, пустой фильтр не фильтрует.

- `SearchUp` — первые `take` записей от `from_time`, по возрастанию `timestamp`. Читать дальше — тот же запрос с `from_time` после последней полученной записи.
- `SearchDown` — последние `take` записей до `to_time`, по убыванию `timestamp`. Читать дальше — тот же запрос с `to_time` перед последней полученной записью.

### CTX Search (`Read` gRPC)

Точное совпадение пар `key=value` в контексте лога (`Process` тоже считается ключом). Регистронезависимо. То же, что `SearchDown` без фразы; оставлен, пока UI не перешёл на `SearchUp`/`SearchDown`.

- UI шлёт `context_keys: Vec<{key, value}>`, `levels`, `from_time`, `to_time`, `take`.
- Возвращает поток `LogEventGrpcModel` по убыванию `timestamp`: последние `take` записей интервала.

### Text Search (`ScanAndSearch` gRPC)

Поиск подстроки без учёта регистра в `message`, `process` и **значениях** контекста (без ключей). Синтаксиса запросов нет: AND/OR/NOT, кавычки и префиксы не разбираются, фраза ищется как есть. То же, что `SearchDown` с одной фразой.

- UI шлёт `phrase`, `from_time`, `to_time`, `take`.
- Результат — как в CTX Search.

## Storage layout

### Логи

На час — файлы данных `YYYYMMDDHH.data00`, `.data01` … `.dataFF`, `YYYYMMDDHH.index` и `YYYYMMDDHH.index-by-key`. Файл данных берёт новые фреймы, пока не дорос до 3 ГиБ, дальше — следующий; новый фрейм вставки в старый файл тоже идёт в последний, так что файлы не перерастают порог больше чем на фрейм:

- `<LogsDbPath>/logs/` — Warning, Error, FatalError;
- `<LogsDbPath>/debug-info/` — Debug, Info.

`.dataNN` — фреймы по 32 KiB в формате рабочих фреймов archived-data: заголовок `size u32 · next_file u8 · next u32 · used u16`, затем `used` байт записей. Фреймы всех файлов часа — одна цепочка в порядке времени, `next_file · next` — следующий фрейм, в том же файле или в другом, у последнего — нет. Запись — `[varint длина][время i64][блок zstd]`: записи логов одной секунды в protobuf, каждая с varint-длиной (`UInt32VariableSize` из rust-extensions), сжатые вместе, не больше 8 KiB. В секунде может быть несколько блоков.

`.index` — 3600 ячеек `file u8 · offset u32 · count u32`, по одной на секунду часа: файл данных первой записи секунды, её смещение в нём и сколько в секунде записей. Следом один байт: 0 — ячейки соответствуют файлу данных. Сброс на диск ставит 1 до записи фреймов и 0 вместе с ячейками; индекс с 1 при открытии перестраивается обходом цепочки.

`.index-by-key` — для уровня, process, `Application`, `Version` и ключей из `InsightsKeys`: сколько записей каждой секунды имеют каждое значение (в нижнем регистре). Сначала каталог — ключи, значения и где лежат их секунды, — дальше, упакованно, секунды, где значение есть: `varint(шаг от предыдущей секунды) · varint(количество)`, 2–3 байта на секунду. Ключ с больше чем 1000 значений за час в этом часе не индексируется. Для текущего и прошлого часа держится в памяти целиком — его формируют записи; на диск пишется не чаще раза в 5 секунд, при запечатывании часа и при остановке; если он не сходится с суммой `count` основного индекса — пересобирается по данным. У более старого часа — что с диска, что из S3 — в память читается только страница ключей и значений: одно чтение 64 KiB с начала файла, по заголовку видно, нужно ли дочитать страницу; что чтение принесло после страницы, остаётся в памяти, так что индекс короче одного чтения читается один раз. Секунды значения, которых ещё нет, подгружаются, когда фильтр их спрашивает, — блоки ближе 64 KiB друг к другу одним чтением, всегда вперёд, — и остаются в памяти.

Запись:

- записи 5 секунд ждут в памяти, по секундам, — опоздавшие попадают в блок своей секунды;
- новые записи уже записанной секунды вливаются в её последний блок: блок распаковывается, записи добавляются, блок сжимается заново и встаёт на своё место;
- вставка в середину не двигает файл: во фрейме с местом сдвигаются записи после места вставки; полный последний фрейм получает новый следом; полный фрейм в середине делится пополам, верхняя половина уходит в следующий фрейм или в новый фрейм в конце файла, вставленный в цепочку. Пишутся только изменённые фреймы, ячейки едут вместе с записями;
- индексы текущего и прошлого часа всегда в памяти, остальные часы открываются на чтение и закрываются после 10 минут простоя.

### Hourly statistics

In-memory `BTreeMap<StatisticsHour, BTreeMap<Application, Counters>>`. Обновляется синхронно из `flows::post_items::update`. Персистится в `<LogsDbPath>/statistics.json` каждые 60 секунд таймером `PersistStatisticsTimer`. На старте `flows::init` восстанавливает структуру из этого файла. `GetStatistic` отдаёт счётчики текущего часа по всем приложениям.

### Ignore events

JSON-файл `<LogsDbPath>/settings.json`. Перезаписывается полностью при каждом изменении (add/delete). Читается на старте.

## Retention

- `GcTimer` (раз в 30 секунд):
  - удаляет часы `debug-info/` через 2 часа после конца часа;
  - удаляет часы `logs/` старее `hours_to_gc` (с S3 они к этому времени уже выгружены);
  - удаляет остатки старого хранилища (`logs-YYYYMMDDHH/` Tantivy, `debug|info/logs-*.db` sqlite) по тем же срокам;
  - `hourly_statistics.gc()` оставляет максимум 48 часов в памяти.
- `UploadToS3Timer` (раз в минуту, если заданы `S3Settings`):
  - час `logs/` через 2 часа после конца запечатывается (записи в него больше не принимаются) и копируется для выгрузки: данные — фреймами подряд, каждый заполнен до конца, после 3 ГиБ — в следующий файл, так что чтение идёт от ячейки секунды только вперёд, без прыжков; индекс — с новыми смещениями; индекс по ключам — целиком, страница ключей первой. Выгружается как `<prefix>/YYYYMMDDHH.data00` …, `.index-by-key`, `.index` — данные, индекс по ключам, индекс последним; prefix — `logs`, если в настройках не задан — и удаляется локально; поиск читает такие часы из S3;
  - раз в 10 минут удаляет из S3 часы старее `hours_to_gc`.
- Записи, пришедшие для часа, который уже выгружен или удалён, отбрасываются (сообщение в debug console).

## MCP server

Endpoint: `POST/GET/DELETE /mcp` (тот же HTTP-порт, что и REST/swagger). Streamable HTTP transport (JSON-RPC 2.0 + SSE), реализован через `mcp-server-middleware` поверх `my-http-server`. Регистрация — в [`src/http/start_up.rs`](../src/http/start_up.rs).

Сейчас зарегистрирован один tool: **`search_logs`** ([src/mcp/search_logs_tool_call.rs](../src/mcp/search_logs_tool_call.rs)).

### `search_logs` — параметры

Все опциональны кроме описанной комбинации `last_minutes` или `(from_time, to_time)`.

| Поле              | Тип             | Назначение                                                                 |
|-------------------|-----------------|----------------------------------------------------------------------------|
| `phrase`          | `string`        | Подстрока без учёта регистра в message, process и значениях контекста. Пустое или отсутствует — без фразы. |
| `last_minutes`    | `integer`       | Если > 0 — диапазон `[now - N min .. now]`. Перебивает `from_time`/`to_time`. |
| `from_time`       | `integer` (us)  | Используется только если `last_minutes` отсутствует/0. Парный с `to_time`. |
| `to_time`         | `integer` (us)  | Парный с `from_time`. Должно быть `from_time < to_time`.                   |
| `levels`          | `string[]`      | Допустимы: `info`, `warning`, `error`, `fatal_error`, `debug`. Регистронезависимо. |
| `context_filters` | `string[]`      | Каждая запись `key=value`. Регистронезависимое точное совпадение.          |
| `take`            | `integer`       | Максимум записей. Default 100, диапазон 1..1000.                           |

### `search_logs` — ответ

Поле `items_json` — строка с JSON-массивом последних `take` записей интервала по возрастанию `timestamp`. Каждый элемент:

```json
{
  "timestamp": 1714060800123456,
  "iso_time": "2026-04-25T22:00:00.123456+00:00",
  "level": "Error",
  "message": "...",
  "context": { "Application": "Billing", "Version": "1.4.2", "Process": "ingest" }
}
```

### Резолв временного интервала (одно правило для AI)

```
if last_minutes > 0:
    from = now - last_minutes minutes
    to   = now
elif from_time > 0 and to_time > 0:
    use as-is
else:
    error
```

### Под капотом

Tool вызывает [`flows::search_logs`](../src/flows/search_logs.rs) → [`LogsStorage::search`](../src/logs_storage/logs_storage.rs) — тот же путь, что и gRPC `Read`/`ScanAndSearch`, только с фильтрами уровня, контекста и фразой одновременно.
